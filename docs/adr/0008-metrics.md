# ADR-0008. Метрики сервера и агента

Статус: принято.

## Контекст

Критерии надёжности этапа 0 (`ROADMAP.md`) нечем проверить в эксплуатации. Состояние агента видно только в Dashboard, то есть только пока работает центр. Каждый отказ из таблицы «Отказы» в `ARCHITECTURE.md` должен быть виден оператору. При этом метрики читают люди и системы, которым данные не доверены: мониторинг заказчика, оператор платформы.

## Решение

1. **Формат Prometheus, библиотека `client_golang`** с закреплённой версией. Метрики рантайма Go и процесса включены.
2. **Значения меток только из закрытых наборов.** Пакет `internal/platform/metrics` принимает метку одного из видов:
   - перечисление;
   - код вида `TARGET_NOT_ALLOWED`;
   - UUID;
   - шаблон маршрута вида `GET /api/v1/sources/{id}`.

   Значение не того вида заменяется на `INVALID` и считается в `*_metric_label_rejections_total`. Так значение, имя объекта или текст ошибки не может попасть в метку, даже если код передаст его по ошибке. Это тот же принцип, что у Egress Guard: заблокировать, а не переписать.
3. **Метрики сервера не называют арендаторов, агентов и источники.** Оператор платформы не должен узнавать об арендаторе через метрики. Кроме того, роль сервера в PostgreSQL не читает данные нескольких арендаторов сразу. REST считается по шаблону маршрута, а не по пути: в пути бывают идентификаторы.
4. **Метрики сервера — на отдельном порту** (`DG_METRICS_ADDR`), без аутентификации. Порт открывается только во внутренней сети. API метрик не отдаёт, а сборщику метрик не нужен доступ к API.
5. **У агента порт метрик выключен по умолчанию.** Он открывается адресом `metrics.address` в `agent.yaml` и отдаёт только `GET /metrics`. Это первый слушающий порт агента. Он только читает: ни один запрос не меняет агента и не доходит до источника. В метках агента есть `source_id` — идентификатор, который заказчик и так видит в центре. Имён, адресов и учётных записей источников в метриках нет.
6. **Состояние читается в момент сбора.** Очередь, состояние сборщиков, отказы источников и срок сертификата агент уже хранит для heartbeat. Метрика вычисляется из того же состояния при каждом чтении и не может разойтись с тем, что видит центр. Удалённый источник пропадает из метрик, а не замирает на последнем значении. Счётчики стоят там, где событие происходит: вызов центра, запись в очередь, блокировка Guard, отклонённая политика.
7. **Ядро не знает о метриках.** Приём событий сообщает о себе через порт `audit.Observer`: только числа сохранённых событий и дублей и задержки.

## Последствия

- Задержка от записи в журнале СУБД до записи в центре измеряется гистограммой `dataguard_server_event_delivery_delay_seconds`. Повтор после простоя агента честно попадает в верхние корзины.
- Мониторинг заказчика видит отказ центра, заполнение очереди и слепоту источника по метрикам агента, даже когда центр недоступен.
- Порт метрик агента без аутентификации. Его стоит открывать на `127.0.0.1` или на адресе за межсетевым экраном. Метрики не содержат значений, но показывают, какие источники есть и в каком они состоянии.
- Дешёвая проверка утечек: сквозной тест ищет исходные значения в ответах обоих портов метрик.
