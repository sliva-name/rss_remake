# ADR-0012. Совместимость агента и центра

Статус: принято.

## Контекст

Агент стоит у заказчика и обновляется по его графику, центр — по графику платформы. Поэтому какое-то время в установке работают агенты разных версий. До этого решения версия агента записывалась при регистрации и в heartbeat, но не проверялась. Центр принимал только одну версию конверта (`Envelope.schema_version`). Агент, которому центр отказывал, выглядел в Dashboard просто молчащим, и оператор не мог узнать почему.

## Решение

1. **Совместимость определяет версия контракта, а не версия агента.** Контракт — это `schema_version` в конверте каждого запроса. Версия агента вида `0.1.0` нужна только людям: центр её показывает, но не сравнивает.
2. **Центр принимает окно версий** от `MinSchemaVersion` до `CurrentSchemaVersion` (`internal/server/agentapi`). Добавлять поля можно без новой версии: proto3 пропускает неизвестные поля. Новая версия нужна для несовместимого изменения. Тогда центр ещё один выпуск принимает и предыдущую версию.
3. **Порядок обновления: сначала центр, потом агенты.** Агент новее центра получает отказ, пока не обновят центр. События при этом не теряются, но копятся в очереди агента.
4. **Отказ объясняется.** Запрос с версией вне окна получает `FailedPrecondition` и код `CONTRACT_UNSUPPORTED`. Центр записывает предложенную версию агенту (`agents.refused_contract_version`), а Dashboard показывает агента как «Центр не принимает версию агента» с действием из `failures.json`. Принятый heartbeat снимает отметку и записывает версию контракта (`agents.contract_version`). В журнале агента отказ виден строкой `center refused the agent version` с тем же кодом.
5. **Регистрация проверяет контракт до того, как тратит токен.** `EnrollRequest.schema_version` агент заполняет сам. Ноль приходит от агентов, выпущенных до этого поля, и считается версией 1. Если оператор поставил не ту версию агента, он регистрирует правильную с тем же токеном.

## Последствия

- Агент вне окна продолжает читать журналы и складывать события в очередь. Когда она заполнится, начинает действовать правило из таблицы «Отказы» в `ARCHITECTURE.md`: позиция журнала стоит, записи ждут в журнале СУБД.
- По `contract_version` в списке агентов видно, можно ли поднять `MinSchemaVersion`: на старом контракте не должно остаться ни одного агента.
- Сейчас окно состоит из одной версии 1. Механизм проверяет тест `TestCenterRefusesAContractItDoesNotSpeak`: версии на единицу выше и ниже окна.
