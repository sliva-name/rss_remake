# ADR-0001. Отступления от исходной архитектуры в MVP

Статус: принято.

## Контекст

Спецификация описывает полную платформу. Принцип §17 требует минимального корректного решения, а §2 запрещает слои и сервисы без конкретной необходимости.

## Решение

1. **Без Redpanda в MVP.** Агент доставляет события в ingest напрямую. Буфер — надёжная очередь агента. Подтверждение только после записи в ClickHouse. Брокер можно добавить за портом `EventSink`, контракт агента при этом не меняется. §7.1 такой путь допускает.
2. **Без Redis.** Для него нет задачи в MVP.
3. **Парсеры только на Go, без SQLGlot.** Сервис на Python потребовал бы либо второго runtime у агента, либо передачи SQL с литералами из процесса агента. Второе нарушает главное требование безопасности.
4. **Корреляция нескольких источников отложена.** В MVP один источник событий, native audit. Есть дедупликация и привязка контекста приложения внутри транзакции.
5. **Подтверждённый контекст приложения только для PostgreSQL.** Для остальных СУБД `application_context` не заявляется, атрибуция идёт до DB principal.
6. **`credential_ref` не хранится в центре.** Сверх плана: центр знает только `source_key`. Так он узнаёт о подключениях ещё меньше.

## Последствия

- Первая установка требует только PostgreSQL, ClickHouse и OIDC-провайдера.
- Нет повторной обработки событий из брокера. Её заменяет таблица `audit_evidence`, из которой можно пересчитать операции.
- Прокси и второй источник событий потребуют отдельного решения по корреляции.
