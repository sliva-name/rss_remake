# ADR-0001. Отступления от исходной архитектуры в MVP

Статус: принято.

## Контекст

Спецификация описывает полную платформу. Принцип §17 требует минимального корректного решения, а §2 запрещает слои и сервисы без конкретной необходимости.

## Решение

1. **Без Redpanda в MVP.** Агент доставляет события в ingest напрямую. Буфер — надёжная очередь агента. Подтверждение только после записи в ClickHouse. Брокер можно добавить за портом `EventSink`, контракт агента при этом не меняется. §7.1 такой путь допускает. Пункт заменён ADR-0009: события идут через Redpanda.
2. **Без Redis.** Для него нет задачи в MVP.
3. **Парсеры только на Go, без SQLGlot.** Сервис на Python потребовал бы либо второго runtime у агента, либо передачи SQL с литералами из процесса агента. Второе нарушает главное требование безопасности.
4. **Корреляция нескольких источников отложена.** В MVP один источник событий, native audit. Есть дедупликация и привязка контекста приложения внутри транзакции.
5. **Подтверждённый контекст приложения только для PostgreSQL.** Для остальных СУБД `application_context` не заявляется, атрибуция идёт до DB principal.
6. **`credential_ref` не хранится в центре.** Сверх плана: центр знает только `source_key`. Так он узнаёт о подключениях ещё меньше. Пункт заменён ADR-0006: центр хранит описание источника и пароль, запечатанный ключом агента.
7. **Одна таблица событий вместо `audit_evidence` и `access_operations`.** При одном источнике свидетельство и операция соотносятся один к одному. Вторая таблица появится вместе со вторым источником.
8. **Без материализованного представления.** `ReplacingMergeTree` дедуплицирует только при чтении, а представление считало бы дубли. Отчёты читают базовую таблицу с `FINAL`. Если объём потребует ускорения, нужен агрегат на `uniqExactState(event_id)`. Замер на 100 млн событий показал, что ускорение нужно, а путь через `uniqExactState` неудачен. Заменён ADR-0007: дедупликация при приёме и агрегатная проекция.

## Последствия

- Первая установка требует только PostgreSQL, ClickHouse и OIDC-провайдера.
- Нет повторной обработки событий из брокера. Её заменяет таблица `audit_events`, из которой можно пересчитать отчёты.
- Прокси и второй источник событий потребуют отдельного решения по корреляции.
