# ADR-0013. Журнал действий операторов

Статус: принято.

## Контекст

Проверяющему нужно знать, кто добавил или изменил источник, опубликовал политику, выпустил токен, зарегистрировал или отозвал агента. До этого решения автор сохранялся только у политики и сканирования, остальные действия не оставляли следа. Журнал нужен именно тогда, когда что-то пошло не так. Поэтому он не должен терять записи при сбое и не должен поддаваться правке задним числом.

## Решение

1. **Запись пишется в транзакции самого действия.** Сервис ядра собирает запись (`internal/core/oplog`), хранилище вставляет её в той же транзакции, что и изменение. Изменение без записи зафиксировать нельзя, а запись без изменения не появится. Триггеры PostgreSQL отклонены: каждой таблице понадобились бы свои правила, чтобы отличить действие оператора от изменения, которое сделал агент (heartbeat, отчёт об источнике).
2. **Журнал только растёт.** У роли сервера `dg_runtime` на `operator_actions` есть только `INSERT` и `SELECT`, а `UPDATE`, `DELETE` и `TRUNCATE` отозваны. Даже взломанный сервер не перепишет, кто что сделал. Записи изолированы по организации той же политикой строк, что и остальные таблицы.
3. **Автор — из токена OIDC.** Сохраняются `sub` и `preferred_username` на момент действия: если пользователя переименуют, запись останется прежней. Агент регистрируется по токену, поэтому его регистрация записывается на того, кто выпустил токен. Действие, за которым нет запроса оператора, записывается от имени платформы, с пустым `sub`.
4. **В записи нет значений.** Изменение источника называет поля (`changes: host,port,password`), но не их значения. Пароль упоминается только как поле: центр не может его прочитать. Публикация политики хранит номер версии.
5. **Черновик источника в журнал не попадает.** Проверка подключения создаёт и удаляет черновики, и это шум. Для журнала источник создан, когда его сохранили (`source.create`). Сохранение без изменений не записывается.
6. **Объект — то, на что указывает запись.** Токен выпускается для среды, сканирование запускается для источника, политика принадлежит организации. Поэтому у этих записей `objectId` — среда, источник и организация. Тип объекта API отдаёт отдельно (`objectKind`). Имя объекта сохраняется на момент действия: объект могут переименовать или удалить.
7. **Читают администратор и аудитор организации** (`listOperatorActions`), аналитик — нет. Журнал есть в разделе «Журнал действий», а также на страницах источника и агента.

## Последствия

- Автор токена хранится в `enrollment_tokens`, иначе регистрацию агента не к кому отнести.
- Срока хранения у журнала нет: записей немного, по одной на действие оператора. Когда понадобится очистка, её выполнит отдельная роль-владелец, а не роль сервера.
- Действия администратора платформы, например создание организации, записываются в журнал этой организации: другого журнала у платформы нет.
- Что каждое действие оставляет запись с автором и что роль сервера не может изменить журнал, проверяют тесты `TestJournalRecordsWhoDidWhat` и `TestJournalOnlyGrows`.
