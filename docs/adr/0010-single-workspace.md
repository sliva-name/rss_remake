# ADR-0010. Единое рабочее пространство

Статус: принято. Требование владельца от 08.11.2026.

## Контекст

Пользователи DataGuard — администратор организации, аналитик безопасности, аудитор, администратор платформы. Требование: одно рабочее пространство для всех, а различия между пользователями задают только разрешения, а не отдельные интерфейсы или разная навигация.

Dashboard уже одно приложение, но решения о видимости он принимает по названиям ролей:

- раздел «Инфраструктура» сравнивает `roles` со строками `tenant_admin` и `security_analyst`;
- оболочка выбирает набор разделов по признакам «есть организация» и «администратор платформы».

Правила доступа поэтому живут в двух местах: в `accessRules` на сервере и в проверках интерфейса. Новая роль или изменённое правило требует правки обоих, и интерфейс может разойтись с API: показать кнопку, на которую API ответит 403, или спрятать разрешённое.

Ещё нет страниц объектов и переходов между ними, глобального поиска, сохранённых представлений, избранного и настройки обзора.

## Решение

1. **Одно приложение, одна навигация.** Разделы названы по задачам: что есть в данных, кто к ним обращается, что платформа видит, что показать проверяющему. Список разделов одинаков для всех. Раздел, в котором пользователю недоступна ни одна операция, не показывается. Других различий в навигации нет.
2. **Разрешение — это операция API.** `GET /me` отдаёт `permissions`: операции, которые пользователь может вызвать, в именах `operationId` из OpenAPI. Сервер вычисляет их из тех же `accessRules`, по которым проверяет вызовы, поэтому список не может разойтись с проверкой. Это закреплено тестом.
   - Интерфейс показывает элемент, если разрешена операция, которую он вызывает. Названий ролей интерфейс не знает.
   - Роли остаются способом выдачи разрешений в провайдере входа. У пользователя с несколькими ролями разрешения объединяются.
   - Администратор платформы без организации видит только «Организации». Это следует из правил: остальные операции требуют организации. Отдельной ветки в интерфейсе для него нет.
3. **Защита — только на сервере.** Скрытый элемент — удобство, а не защита. Каждая операция проходит `authorize`, операция без правила запрещена. Правило проверяет и роль, и принадлежность организации. Изоляцию данных дополнительно держат RLS и row policy.
4. **ABAC добавляется в ту же точку.** Когда доступ начнёт зависеть от атрибутов объекта (среда, источник, категория), проверка останется на сервере: списки вернут только доступные объекты, а ответ об объекте перечислит доступные над ним операции. `permissions` в `/me` останется ответом на вопрос «какие операции бывают доступны», а не «над каким объектом».
5. **У каждого объекта есть страница с адресом.** Цепочка: источник → агент → база → схема → таблица → колонка → классификация → события аудита. Список ссылается на страницу объекта, страница — на соседей по цепочке и на события, отфильтрованные по объекту. Объект показывается на одной странице. Другие разделы ссылаются на неё, а не повторяют её содержимое.
6. **Фильтры живут в адресе.** Любое состояние списка — это ссылка: её можно сохранить, отправить коллеге, открыть в новой вкладке. Сохранённое представление — это раздел и параметры адреса с именем.
7. **Личные настройки хранятся в центре.** Сохранённые представления, избранные объекты и раскладка обзора лежат в PostgreSQL под RLS с ключом `(tenant_id, subject)`. Не в `localStorage`: они должны переживать смену браузера и компьютера. Хранятся только ссылки на объекты и параметры фильтров, значений данных там нет: интерфейс их не получает.
8. **Глобальный поиск — по метаданным.** Ищутся источники, агенты, таблицы, колонки и пользователи СУБД по имени. Каждая группа результатов возвращается, только если пользователю разрешена операция, которая перечисляет такие объекты. Значения не ищутся: их нет в центре.
9. **Обзор собирается из виджетов.** Каждый виджет объявляет операции, которые ему нужны. Недоступный виджет не предлагается. По умолчанию показаны все доступные, пользователь может убрать лишние и поменять порядок.
10. **Вопрос пользователя — тоже объект со страницей.** «Кто обращался к паспортным данным» не должен требовать обхода каталога, журнала и отчёта с ручной сверкой. У категории данных есть своя страница: где она хранится, кто к ней обращался и что делал. Счётчики на ней считаются по этой категории на сервере, а не выбираются из общих итогов в браузере.
11. **Функции этапа 2 `ROADMAP.md` встраиваются в эту схему.** Разбор классификации живёт на странице колонки, расписание сканирования — на странице источника, редактор политик — в разделе настроек организации. Новых разделов под отдельные роли не появляется.

## Последствия

- Новая роль заводится в провайдере входа и в `accessRules`. Интерфейс менять не нужно.
- Правило доступа меняется в одном месте, интерфейс следует за ним без правки.
- Тест сверяет список операций OpenAPI с `accessRules` и `permissions` с `checkAccess`. Операция без правила не соберётся в зелёный `make check`.
- Каждая новая страница объекта требует операции чтения объекта и фильтра событий по нему. События фильтруются по источнику, таблице, колонке, пользователю, категории, типу и сессии.
- Личные настройки — первые данные центра, принадлежащие человеку, а не организации. Они лежат в `user_preferences` по ключу на настройку: представления, избранное, недавние, раскладка обзора, до 64 КиБ каждая. Политика строк сравнивает и организацию, и `subject` из токена: сервер ставит `app.subject` в транзакции, поэтому даже ошибка в запросе не отдаст чужие настройки. Администратор организации их тоже не видит. При удалении учётной записи в провайдере входа они остаются, пока их не удалит оператор базы; операция удаления появится вместе с журналом действий операторов (этап 1).
