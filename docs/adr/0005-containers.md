# ADR-0005. Каждая часть платформы работает в контейнере

Статус: принято.

## Контекст

Сервер, агент, интерфейс и разовые задачи (миграции, выпуск PKI) запускались как бинарники на хосте. Требование: каждая часть работает в Docker. Контейнеры не должны ослабить границы доверия из `SECURITY_MODEL.md`.

## Решение

1. **Один `Dockerfile` с целями `server` и `agent`.** Сборка идёт в образе Go, итоговые образы собраны на `distroless/static`: без оболочки и пакетного менеджера, пользователь без root. Базовые образы закреплены по дайджесту.
2. **Интерфейс входит в образ сервера.** Его собирает стадия Node, сервер раздаёт статику с политикой CSP из `app.webHandler`. В отдельном контейнере с nginx пришлось бы дублировать эту политику и проксировать API. Тогда интерфейс и API разошлись бы по разным источникам, и CSP пришлось бы ослабить.
3. **Разовые задачи — сервисы того же образа сервера.** `pki-init` с ключом `--keep-existing` можно запускать при каждом старте: если CA уже есть, задача ничего не меняет. `migrate` запускается после него. Сервер стартует только после их успешного завершения.
4. **Ключ CA остаётся в томе центра.** `pki-init` кладёт копию сертификата CA в отдельный том `center-ca`. Агент монтирует только его, только для чтения. Ключи CA и политик агенту не видны.
5. **Учётные данные СУБД агент получал как secrets compose** (`/run/secrets/...`), а не через переменные окружения. Пункт заменён ADR-0006: пароли приходят из центра запечатанными, а в `agent.yaml` остался список разрешённых целей.
6. **Токен регистрации агент читает со стандартного ввода** (`--token-file /dev/stdin`). Токен не попадает ни в командную строку, ни в образ, ни в том.
7. **Адрес OIDC для сервера можно задать отдельно** (`DG_OIDC_DISCOVERY_URL`). Браузер видит Keycloak на опубликованном порту, сервер — по имени в сети compose. Издатель в токене проверяется по `DG_OIDC_ISSUER` в любом случае: провайдер обязан объявить именно его.
8. **Проверка в браузере — тоже контейнер** (`web/dashboard/e2e/Dockerfile`, образ Playwright). Он работает в сети хоста, чтобы открывать платформу по тем же адресам, что и пользователь: этого требуют адреса возврата OIDC.
9. **Инициализация SQL Server выполняется внутри его контейнера.** Здоровым он считается только после того, как созданы учётные записи и аудит. Иначе `docker compose up --wait` падает на завершившемся разовом контейнере.

## Последствия

- `make dev-up` поднимает весь стенд вместе с центром. Агент запускается после регистрации: `make agent-enroll`, затем `make agent-up`.
- Сквозной тест управляет контейнерами через `docker compose`: `kill -9` — это `docker compose kill --signal SIGKILL`. Очередь агента он проверяет на копии тома, снятой `docker cp`.
- Пароли центральных PostgreSQL и ClickHouse сервер получает через переменные окружения. Их видит любой, у кого есть доступ к Docker API, то есть фактически root на хосте. Для промышленной установки нужны файлы секретов. В MVP этого нет.
- Интеграционные и нагрузочные тесты по-прежнему поднимают сервер внутри процесса теста. Это проверка кода, а не развёртывания.
