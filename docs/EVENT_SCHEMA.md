# Схема событий

Источник истины — `api/proto/dataguard/agent/v1/events.proto`. Этот документ фиксирует смысл полей: его нельзя вывести из типов.

## Что считается обращением к данным

Событие — это **свидетельство**, а не утверждение о факте чтения. Уровень свидетельства указан явно и никогда не завышается.

| `EvidenceLevel` | Что доказано | Источник в MVP |
|---|---|---|
| `REFERENCED` | Запрос упоминает объект | MySQL Community `general_log` |
| `EXECUTED` | Запрос успешно выполнен | pgAudit, MariaDB, SQL Server Audit |
| `ROWS_CONFIRMED` | СУБД подтвердила возврат строк | В MVP не формируется |
| `DELIVERED` | Данные получены приложением | В MVP не формируется |

Отчёты не имеют права показывать `REFERENCED` как «пользователь прочитал данные».

## Личность инициатора

| `IdentityConfidence` | Значение |
|---|---|
| `VERIFIED` | Контекст подписан приложением, подпись и срок проверены |
| `DB_PRINCIPAL_ONLY` | Известна только учётная запись СУБД |
| `UNVERIFIED_CLAIM` | Контекст есть, но подпись неверна или просрочена |
| `UNKNOWN` | Личность установить нельзя |

Интерфейс показывает `UNKNOWN` как «Не идентифицирован». Угадывать сотрудника по IP или учётной записи запрещено.

В событиях хранится стабильный `application_principal` (subject id), а не отображаемое имя.

## Разрешение объектов

| `ObjectResolution` | Значение |
|---|---|
| `RESOLVED` | Все объекты сопоставлены с каталогом до колонок |
| `PARTIAL` | Сопоставлена часть объектов, например таблицы без колонок |
| `UNRESOLVED` | Запрос не разобран: динамический SQL, неизвестный синтаксис |

При `UNRESOLVED` нет ни текста запроса, ни fingerprint. Имена в событии — только объекты, найденные в каталоге.

## Идентификатор и дедупликация

`event_id` выводится из `source_id` и позиции в журнале (UUIDv5). Повтор после сбоя агента даёт тот же идентификатор. Время события агент фиксирует до записи в очередь: время журнала позже 1 минуты вперёд или старше 364 дней заменяется его часами. Поэтому повтор несёт и то же время. Подтверждение от сервера значит, что событие надёжно записано в брокер (ADR-0009). Потребитель брокера ищет пару `(event_time, event_id)` по первичному ключу ClickHouse и уже записанное не вставляет. Запись событий одного агента идёт под блокировкой, поэтому повтор агента, повторное чтение после сбоя потребителя и партиция, переехавшая к другому экземпляру, не дают дубля (ADR-0007).

`query_fingerprint` — это класс запроса, а не выполнение: один fingerprint встречается тысячи раз. Для выполнения служат `event_id` и `Correlation`.

## Потеря наблюдаемости

`AUDIT_GAP` фиксирует период, в котором события могли быть потеряны:

| `GapReason` | Причина |
|---|---|
| `QUEUE_FULL` | Очередь агента заполнена |
| `LOG_ROTATED` | Журнал ротирован раньше, чем агент его дочитал |
| `SOURCE_UNAVAILABLE` | Источник журнала недоступен |
| `UNPARSEABLE_RECORDS` | Записи журнала не удалось разобрать |

`lost_events` отсутствует, если размер потери неизвестен. Значение 0 в этом случае было бы ложью.

`AuditSourceHealth` приходит с heartbeat и различает «нет активности» (`OBSERVING`) и «нет возможности видеть» (`UNAVAILABLE`).

## Эволюция схемы

- Каждый запрос несёт `Envelope.schema_version`.
- Изменения только совместимые: `buf breaking` (режим `WIRE_JSON`).
- Удалённые поля резервируются, номера не переиспользуются.
- Новое строковое поле обязано объявить `FieldKind`.
