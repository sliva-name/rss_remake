# Установка

Как поставить центр DataGuard на сервер заказчика и подключить к нему агентов. Порядок шагов проверяет `make test-install`: тест ставит центр с нуля по этой инструкции, регистрирует агента, делает резервную копию и восстанавливает её.

## Что ставится

- **Центр** — `deployments/production/compose.yml`, один хост. В нём PostgreSQL, ClickHouse, Redpanda, сервер с Dashboard и, при желании, Keycloak. Наружу открыты три порта: Dashboard, порт агентов и Keycloak, если он включён.
- **Агент** — `deployments/agent/compose.yml`, на хосте в сети заказчика, рядом с базами. Он подключается к центру сам, только исходящими соединениями. Входящих портов у агента нет.

## Требования

**Программы:** Docker Engine с Compose 2.24 или новее и `openssl`.

**Ресурсы центра.** Эталонная нагрузка — 100 млн событий за 30 дней, около 40 событий в секунду, в пике 400. Все замеры `ROADMAP.md`, этап 0, сделаны на хосте с 8 ядрами и 15 ГБ памяти. На нём центр укладывается во все цели.

| Что | Сколько | Откуда цифра |
|---|---|---|
| Процессор и память | 8 ядер, 16 ГБ | Замеры этапа 0 |
| ClickHouse | около 10,5 ГиБ на 100 млн событий, срок хранения 13 месяцев: при эталонной нагрузке около 135 ГиБ | Замер: 10,2 ГиБ строк и 225 МиБ агрегата на 100 млн |
| Redpanda | события за 7 дней: при эталонной нагрузке около 10 ГиБ | Оценка, не замер |
| PostgreSQL | единицы гигабайт: каталог, источники, журнал | Оценка |

**Сеть.** Браузеры пользователей ходят на порт Dashboard, агенты — на порт агентов. Если провайдер входа заказчика внешний, сервер должен до него доставать.

## Центр

Команды выполняются в `deployments/production`.

### 1. Настройки

Скопируйте `example.env` в `.env` и заполните. Каждая настройка описана в самом файле. Обязательны:

- `DG_PUBLIC_URL` — адрес Dashboard;
- `DG_AGENT_HOSTS` — имена, по которым агенты обращаются к центру;
- `DG_OIDC_ISSUER` — издатель провайдера входа.

### 2. Сертификат Dashboard

Выпустите сертификат на имя из `DG_PUBLIC_URL` у своего CA. Положите его вместе с цепочкой в `tls/dashboard.crt`, а ключ — в `tls/dashboard.key`. Сервер принимает на порту Dashboard только HTTPS и отдаёт HSTS.

Агентам этот сертификат не нужен. Порт агентов работает на собственном CA центра, его выпускает `pki-init` при первом запуске.

Продление сертификата: скопируйте новый сертификат и ключ поверх старых файлов, сервер подхватит их без перезапуска. Если файлы заменены новыми, выполните `docker compose restart server keycloak`.

### 3. Пароли

```bash
./prepare.sh
```

Скрипт один раз создаёт случайные пароли баз, брокера и Keycloak в `secrets/`. Повторный запуск их не меняет. Сервер читает пароли из файлов, а не из переменных окружения, поэтому через Docker API их не видно (ADR-0005). Каталоги `secrets/` и `tls/` закрыты для других пользователей хоста.

### 4. Провайдер входа

**Свой провайдер OIDC** — вариант по умолчанию. Зарегистрируйте в нём публичного клиента:

- идентификатор — из `DG_OIDC_CLIENT_ID`, по умолчанию `dataguard-dashboard`;
- поток authorization code с PKCE S256;
- адрес возврата `DG_PUBLIC_URL/*`;
- в `aud` access-токена — идентификатор клиента;
- claim `roles` — массив из `platform_admin`, `tenant_admin`, `security_analyst`, `auditor`;
- claim `tenant_id` — UUID организации, у администратора платформы его нет;
- `preferred_username` — его показывает журнал действий.

Если сертификат провайдера выпущен вашим CA, положите этот CA в `tls/oidc-ca.crt` и задайте `DG_OIDC_CA_FILE=/run/secrets/oidc_ca`.

**Keycloak из комплекта** — для тех, у кого своего провайдера нет. Задайте `DG_PUBLIC_HOST`, `DG_KEYCLOAK_PORT` и `DG_KEYCLOAK_URL`, а издатель — `DG_OIDC_ISSUER=${DG_KEYCLOAK_URL}/realms/dataguard`. Запускать с профилем `keycloak`. Keycloak работает по тому же сертификату, что и Dashboard, свои данные хранит в PostgreSQL центра. Консоль администратора — `DG_KEYCLOAK_URL/admin`, пользователь `dg_admin`, пароль в `secrets/keycloak_admin_password`.

### 5. Запуск

```bash
docker compose up --detach --wait
```

С Keycloak из комплекта:

```bash
docker compose --profile keycloak up --detach --wait
```

При каждом запуске `pki-init` проверяет ключи центра, а `migrate` доводит схемы баз до версии образа. Сервер ждёт провайдера входа до двух минут (`DG_OIDC_WAIT`).

### 6. Первые пользователи

1. В провайдере заведите администратора платформы с ролью `platform_admin`.
2. Он входит в Dashboard и создаёт организацию в разделе «Организации».
3. Администраторам и аналитикам организации проставьте `tenant_id` этой организации и их роли.

Администратор платформы данных организаций не видит.

## Агент

Команды выполняются в каталоге с `deployments/agent/compose.yml` на хосте агента.

1. **Сертификат CA центра.** Выполните на центре:

   ```bash
   docker compose --profile backup run --rm --no-deps -T --entrypoint cat backup /pki/ca.crt > ca.crt
   ```

   Перенесите файл на хост агента.

2. **Настройки.** Скопируйте `agent.example.yaml` в `agent.yaml`. В нём укажите адрес центра (`https://<имя из DG_AGENT_HOSTS>:<DG_AGENT_PORT>`) и список разрешённых баз и каталогов журналов. Источник вне этого списка агент не откроет, даже если его потребует центр (ADR-0006). Каталоги журналов смонтируйте в `compose.yml` только для чтения.

3. **Регистрация.** В Dashboard, раздел «Агенты», выпустите токен регистрации и сохраните его в `token.txt`. Токен одноразовый и действует сутки.

   ```bash
   docker compose run --rm -T agent enroll --config /etc/dataguard/agent.yaml --token-file /dev/stdin < token.txt
   ```

4. **Запуск.**

   ```bash
   docker compose up --detach
   ```

   Источники добавляются в Dashboard, пароль запечатывается ключом агента в браузере.

Очередь агента по умолчанию — 256 МиБ, это около 4,5 часа событий при недоступном центре и эталонной нагрузке. Подробнее — в `README.md`.

## Обновление

Сначала центр, потом агенты (ADR-0012). Центр принимает и предыдущую версию контракта агентов.

1. На центре поменяйте `DG_VERSION` и выполните `docker compose up --detach --wait`. Миграции пройдут при запуске.
2. Агентов обновляйте так же, по одному. Агента с версией, которую центр не принимает, Dashboard показывает с причиной «Центр не принимает версию агента». События такого агента ждут в его очереди.

## Резервная копия

```bash
docker compose --profile backup run --rm --no-deps backup backup
```

Копия пишется в `DG_BACKUP_DIR`: `postgres.dump` с базой центра и `pki.tar` с ключами. В копии лежит ключ CA, поэтому храните её зашифрованной и отдельно от центра. Копию тома PKI делайте после каждой замены ключа политик.

ClickHouse в копию не входит (ADR-0015). Без него центр работает, отчёты начнут заполняться заново. Если история событий нужна, настройте `BACKUP` ClickHouse на своё хранилище.

Восстановление:

```bash
docker compose stop server
docker compose --profile backup run --rm --no-deps backup restore
docker compose up --detach --wait
```

После восстановления:

- заново отзовите агентов, отозванных после даты копии;
- зарегистрируйте заново агентов, появившихся после неё;
- введите пароли источников, изменённые после неё.

Агенты, принявшие более новые список источников и политику, получат восстановленные сами.

## Замена ключа подписи политик

```bash
docker compose run --rm --no-deps pki-init rotate-policy-key --dir /var/lib/dataguard/pki
docker compose restart server
```

Агенты берут новый ключ со следующим heartbeat, перерегистрация не нужна (ADR-0014). После замены сделайте резервную копию.

## Мониторинг

Сервер отдаёт метрики Prometheus на порту 9100 внутри сети compose. Чтобы снимать их с хоста, опубликуйте порт на адресе, недоступном снаружи. У агента порт метрик включается в `agent.yaml`. Что показывают метрики, описано в ADR-0008 и в таблице «Отказы» `ARCHITECTURE.md`.

## Чего нет

- Брокер — один узел. Для отказоустойчивости нужен кластер Redpanda из трёх узлов вне этого файла и `DG_BROKER_REPLICATION=3`.
- Helm-чарта нет, установка — compose на одном хосте.
- Замены CA центра нет (ADR-0014).
