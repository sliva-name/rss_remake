# Модель данных

Источник истины — миграции в `migrations/`. Здесь описаны инварианты, которых не видно из DDL.

## Иерархия

```
Tenant
 └─ Environment
     └─ Agent
         └─ Source (экземпляр СУБД)
             └─ Database → Schema → Table → Column
                                              └─ Classification
```

## Инварианты

- **`tenant_id` есть в каждой таблице** с данными арендатора, и на ней включён RLS.
- **Идентификаторы стабильны.** Объект получает UUID при первом обнаружении. Имя — это атрибут, а не ключ.
- **Переименование** определяется при совпадении типа, позиции и классификации в той же таблице. Старое имя пишется в историю. Эвристика может ошибиться, поэтому в истории есть `detected_by`.
- **Объекты не удаляются.** Пропавший объект получает `status = removed` и `last_seen_at`: история обращений к нему остаётся осмысленной.
- **Открытых паролей СУБД в центре нет** (ADR-0006). Источник хранит адрес, базу, пользователя и пароль, запечатанный ключом агента. Центр расшифровать его не может.
- **Источник удаляется мягко.** `deleted_at` выводит его из списка агента и из отчётов, история инвентаря и событий остаётся. Имя освобождается для нового источника с новым id.
- **Источник привязан к агенту навсегда.** События в очереди агента ссылаются на `source_id`. При переносе на другой агент их пришлось бы отвергать.
- **Версия списка источников растёт только вверх** (`agents.sources_version`). Её увеличивает каждое изменение источников агента в той же транзакции.
- **Значений нет.** Нет ни одной колонки для примеров данных.
- **Журнал действий операторов только растёт** (`operator_actions`, ADR-0013). Запись пишется в транзакции самого действия, роль сервера не может её изменить или удалить. Изменение источника хранит имена полей, а не их значения.

## Хранилища

| Данные | Где | Почему |
|---|---|---|
| Арендаторы, агенты, каталог, классификации, задания, политики | PostgreSQL | Связи, транзакции, RLS |
| События и агрегаты | ClickHouse | Большой поток append-only, аналитика |

## Каталог

Имена базы, схемы и таблицы лежат в `asset_tables` как атрибуты, отдельных таблиц `databases` и `schemas` нет. Спецификация предлагала их как часть иерархии, но никаких атрибутов у них в MVP нет, а поиск от этого только усложнился бы.

| Таблица | Назначение |
|---|---|
| `asset_tables`, `asset_columns` | Объекты со стабильными UUID, статусом и `first_seen_at`/`last_seen_at` |
| `asset_renames` | История переименований с указанием, как определено совпадение |
| `classifications` | Категория колонки, confidence и объяснение решения |
| `catalog_changes` | История инвентаря: появление и исчезновение объектов и чувствительных колонок |
| `scan_jobs`, `scan_skipped_tables` | Задания и таблицы, которые не удалось прочитать |

Правила сверки (`internal/core/asset`):
- таблица переименована, если в той же схеме исчезла таблица с тем же отпечатком структуры. Два одинаковых кандидата не сливаются: ошибочное слияние испортит историю, а пропущенное просто заведёт новый объект;
- колонка переименована, если совпали тип и позиция;
- неудачный скан каталог не меняет: пустой снимок ничего не говорит о базе;
- классификация снимается только у таблиц, прочитанных полностью. Отсутствие находки в пропущенной таблице значит «не смотрели», а не «данных нет».

## События

ClickHouse хранит одну таблицу `audit_events`: `MergeTree` с ключом `(tenant_id, event_time, event_id)`, срок хранения 13 месяцев. Повторную доставку отсеивает потребитель брокера перед вставкой, поэтому в таблице каждое событие одно и `FINAL` не нужен. Между приёмом и таблицей события ждут в топике Redpanda `dataguard.audit-events`: Protobuf `dataguard.center.v1.EventRecord`, ключ — агент, срок хранения 7 дней (ADR-0009). Проекция `hourly` считает события по часу и измерениям отчётов. Отчёты читают из неё целые часы, а неполные часы на краях окна — из строк (ADR-0007).

При приёме событие получает снимок классификации из каталога. Позднее изменение классификации историю не переписывает: отчёт показывает то, что считалось верным на момент обращения.

Состояние сборщиков лежит в PostgreSQL, таблица `source_audit_health`.

Задание выдаётся агенту с арендой на 15 минут. Если агент исчез, задание возвращается в работу после истечения аренды, после трёх попыток получает статус `failed`. Повторная отправка результата отклоняется, снимок не применяется дважды.
