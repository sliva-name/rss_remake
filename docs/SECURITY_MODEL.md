# Модель безопасности

Статус: действует с этапа 0. Разделы, ещё не реализованные в коде, помечены «(этап N)».

## Что защищаем

1. **Исходные значения** чувствительных данных. Они не покидают контур заказчика и нигде не сохраняются, даже у агента.
2. **Метаданные и события.** Платформа знает, где лежат данные и кто к ним обращается. Это чувствительная информация второго порядка.
3. **Учётные данные СУБД** заказчика.

## Границы доверия

| Граница | По одну сторону | По другую | Чем защищена |
|---|---|---|---|
| Контур заказчика → центр | Агент (доверенный) | Центр | Закрытая схема, Egress Guard, mTLS |
| Центр → агент | Центр (не полностью доверенный) | Агент | Подпись политик, локальный список целей |
| Приложение → агент | Приложение | Журнал СУБД | Подписанный контекст |
| Оператор → центр | Браузер | API | OIDC, RBAC |
| Арендатор → арендатор | Tenant A | Tenant B | RLS, row policy |

### Почему центру не доверяем полностью

Учётные данные и адреса СУБД хранятся **только у агента**. Центр знает лишь `source_key`, имя источника и сообщает задания по `source_id`.

Взломанный центр не может направить агента на произвольный хост и не получает пароли. Он может запустить сканирование уже настроенного источника, но результат всё равно проходит Egress Guard.

Остаточный риск: политика задаёт custom-детекторы, а счётчик совпадений раскрывает один бит о содержимом колонки. Вредоносная политика теоретически может подбирать значения по одному такому запросу. Смягчения: подпись политик, бюджет скана, журнал версий политик. Полностью риск не закрыт.

## Правила обращения с данными

- Значения читаются только в процессе агента, в памяти, небольшими пакетами. Буфер очищается после обработки.
- Запрещены к отправке: параметры SQL, значения колонок, строки выборок, текст запросов, текст ошибок драйвера, комментарии к колонкам, определения представлений.
- `min`, `max`, `most_common_vals` не собираются: это сырые значения.
- Обычный хеш значения не считается обезличиванием. В MVP значения не хешируются и отдельные записи не идентифицируются.
- `query_fingerprint` считается только от AST после удаления литералов. Если запрос не разобран, fingerprint отсутствует.

## Egress Guard

Каждое строковое и байтовое поле контракта объявляет вид (`FieldKind`). `internal/agent/egress` обходит сообщение рефлексией и проверяет значения по виду.

Свойства:
- новое поле без вида ломает тест `TestEveryOutboundFieldIsClosed`;
- `map`, `Struct`, `Any` запрещены там же;
- нарушение блокирует сообщение целиком, значение не переписывается;
- текст нарушения не содержит значения.

Имена объектов в событиях берутся из каталога через Catalog Resolver (этап 3), а не копируются из текста запроса.

## Журналы и ошибки

- `safelog` пропускает только атрибуты из списка разрешённых, остальные заменяет на `[redacted]`.
- `safeerr` хранит код и статическое описание. Исходная ошибка не сохраняется, поэтому её нельзя распечатать случайно.
- Обычная ошибка в логе заменяется на `[redacted]`.
- Линтер запрещает `fmt.Print*` и `log.*` в коде агента и сервера.
- Текст сообщения лога должен быть статическим. Это правило код-ревью: автоматической проверки нет.

## Идентичность агента (этап 1)

- Enrollment: одноразовый токен → CSR → короткоживущий сертификат внутреннего CA → продление.
- Tenant определяется по сертификату. `tenant_id` в конверте только сверяется.
- Отзыв: статус агента проверяется на каждый запрос.

## Изоляция арендаторов (этапы 1, 4)

- PostgreSQL: RLS под ролью без `BYPASSRLS`, `tenant_id` задаётся через `SET LOCAL` в обёртке транзакции.
- ClickHouse: row policy по настройке сессии, `tenant_id` первым в `ORDER BY`.

## Подделка контекста приложения (этап 3)

`VERIFIED` означает, что контекст подписан ключом приложения и не просрочен. Это подтверждает заявление приложения, а не присутствие человека. Скомпрометированное приложение с настоящим ключом может подписать чужой идентификатор.

## Известные остаточные риски

- **Память.** Go не гарантирует затирание: сборщик мусора копирует объекты, строки неизменяемы. Значения обрабатываются в `[]byte` с очисткой, но дамп памяти агента во время скана может их содержать.
- **Журналы СУБД на стороне заказчика** уже содержат литералы. Агент читает их, но не копирует. Защита самих журналов — задача заказчика.
- **Побочный канал custom-детекторов** описан выше.
