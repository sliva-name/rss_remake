# Модель безопасности

Статус: действует с этапа 0. Разделы, ещё не реализованные в коде, помечены «(этап N)».

## Что защищаем

1. **Исходные значения** чувствительных данных. Они не покидают контур заказчика и нигде не сохраняются, даже у агента.
2. **Метаданные и события.** Платформа знает, где лежат данные и кто к ним обращается. Это чувствительная информация второго порядка.
3. **Учётные данные СУБД** заказчика.

## Границы доверия

| Граница | По одну сторону | По другую | Чем защищена |
|---|---|---|---|
| Контур заказчика → центр | Агент (доверенный) | Центр | Закрытая схема, Egress Guard, mTLS |
| Агент → мониторинг заказчика | Агент | Сборщик метрик | Порт выключен по умолчанию, только чтение, метки из закрытых наборов |
| Центр → агент | Центр (не полностью доверенный) | Агент | Подпись политик и списка источников, локальный список разрешённых целей |
| Приложение → агент | Приложение | Журнал СУБД | Подписанный контекст |
| Оператор → центр | Браузер | API | OIDC, RBAC |
| Арендатор → арендатор | Tenant A | Tenant B | RLS, row policy |

### Почему центру не доверяем полностью

Источники создаются в центре (ADR-0006), но центр не получает паролей и не может направить агента куда угодно.

- **Пароль запечатан в браузере** ключом агента (ECDH P-256, HKDF-SHA256, AES-256-GCM). Шифротекст привязан к арендатору, агенту, СУБД, адресу, порту, базе, пользователю и режиму TLS. Ключ агента создаётся при регистрации, отдельно от ключа mTLS, и не покидает агента.
- **Агент открывает только разрешённое.** Список сетей, хостов и каталогов журналов задаётся при установке агента и обязателен. Цель вне списка агент отклоняет и сообщает код `TARGET_NOT_ALLOWED`.
- **Список источников подписан** ключом политик с отдельным префиксом. Он адресован конкретному агенту, а его версия не может уменьшиться.

Взломанный центр может запустить сканирование настроенного источника, но результат всё равно проходит Egress Guard. Подменённый адрес не откроет старый пароль: это проверяет тест `TestAgentRefusesWhatTheCenterShouldNotAsk`.

Остаточный риск: интерфейс раздаёт центр. Активно взломанный центр может подменить страницу и перехватить пароль в момент ввода. Он может также назначить разрешённый хост со своим паролем и `tls: disable`. Защищены пароли, введённые до взлома, а также утечка базы или резервной копии центра.

Остаточный риск: политика задаёт custom-детекторы, а счётчик совпадений раскрывает один бит о содержимом колонки. Вредоносная политика теоретически может подбирать значения по одному такому запросу. Смягчения: подпись политик, бюджет скана, журнал версий политик. Полностью риск не закрыт.

## Правила обращения с данными

- Значения читаются только в процессе агента, в памяти, небольшими пакетами. Буфер очищается после обработки.
- Запрещены к отправке: параметры SQL, значения колонок, строки выборок, текст запросов, текст ошибок драйвера, комментарии к колонкам, определения представлений.
- `min`, `max`, `most_common_vals` не собираются: это сырые значения.
- Обычный хеш значения не считается обезличиванием. В MVP значения не хешируются и отдельные записи не идентифицируются.
- `query_fingerprint` считается только от AST после удаления литералов. Если запрос не разобран, fingerprint отсутствует.

## Egress Guard

Каждое строковое и байтовое поле контракта объявляет вид (`FieldKind`). `internal/contract/egress` обходит сообщение рефлексией и проверяет значения по виду.

Свойства:
- новое поле без вида ломает тест `TestEveryOutboundFieldIsClosed`;
- `map`, `Struct`, `Any` запрещены там же;
- нарушение блокирует сообщение целиком, значение не переписывается;
- текст нарушения не содержит значения.

Имена объектов в событиях берутся из каталога через Catalog Resolver (этап 3), а не копируются из текста запроса.

## Журналы и ошибки

- `safelog` пропускает только атрибуты из списка разрешённых, остальные заменяет на `[redacted]`.
- `safeerr` хранит код и статическое описание. Исходная ошибка не сохраняется, поэтому её нельзя распечатать случайно.
- Обычная ошибка в логе заменяется на `[redacted]`.
- Линтер запрещает `fmt.Print*` и `log.*` в коде агента и сервера.
- Текст сообщения лога должен быть статическим. Это правило код-ревью: автоматической проверки нет.

## Идентичность агента (этап 1)

- Enrollment: одноразовый токен → CSR → короткоживущий сертификат внутреннего CA → продление.
- Tenant определяется по сертификату. `tenant_id` в конверте только сверяется.
- Отзыв: статус агента проверяется на каждый запрос.

## Брокер событий

ADR-0009. Redpanda стоит между приёмом и ClickHouse и входит в доверенную зону центра, как PostgreSQL и ClickHouse.

- Агенты в брокер не пишут. Арендатора и агента в записи проставляет приём по сертификату, после проверки владения источником.
- В топике лежит то же очищенное событие, что в ClickHouse: значений нет. Срок хранения — 7 дней.
- Вход только по SASL SCRAM, при промышленной установке поверх TLS (`DG_BROKER_CA_FILE`). Учётная запись сервера читает и пишет только свой топик и свою группу. Топики создаёт `migrate` под отдельной учётной записью администратора.
- Топик общий для всех арендаторов, как таблица ClickHouse. Изоляция при чтении остаётся за row policy ClickHouse и RLS PostgreSQL. Доступ к брокеру даёт доступ к событиям всех арендаторов, поэтому его учётные данные защищаются так же, как пароли центральных баз.

## Контейнеры

- Образы `distroless/static` без оболочки, процессы работают под пользователем без root.
- Ключи CA и политик лежат только в томе центра. Агенту монтируется отдельный том с сертификатом CA, только для чтения.
- Паролей СУБД в контейнере агента нет: они приходят запечатанными в списке источников. Токен регистрации агент читает со стандартного ввода.
- `.dockerignore` не пускает в контекст сборки `.env`, журналы аудита стенда и состояние агента.
- Пароли центральных баз и брокера сервер читает из файлов секретов, а не из переменных окружения: переменные видны через Docker API (ADR-0005).

## Метрики

ADR-0008. Метрики читают люди и системы, которым данные не доверены, поэтому:

- значение метки берётся только из закрытого набора: перечисление, код, UUID, шаблон маршрута. Значение не того вида заменяется на `INVALID` и считается. Это проверяет тест `TestLabelValueOutsideItsKindNeverReachesTheEndpoint`;
- метрики сервера не называют арендаторов, агентов и источники, REST считается по шаблону маршрута;
- у агента порт метрик выключен по умолчанию. Включённый, он отдаёт только `GET /metrics` и ничего не меняет. Это единственный слушающий порт агента. Открывать его стоит на `127.0.0.1` или за межсетевым экраном: значений в метриках нет, но видно, какие источники есть и в каком они состоянии;
- сквозной тест ищет исходные значения в ответах обоих портов метрик.

## Изоляция арендаторов (этапы 1, 4)

- PostgreSQL: RLS под ролью без `BYPASSRLS`, `tenant_id` задаётся через `SET LOCAL` в обёртке транзакции.
- ClickHouse: row policy по настройке сессии, `tenant_id` первым в `ORDER BY`.
- Личные настройки (`user_preferences`): политика строк проверяет и организацию, и `subject` пользователя, который сервер задаёт через `SET LOCAL app.subject`. Настройки одного пользователя не видит никто другой, включая администратора организации. Там лежат только ссылки на объекты и параметры фильтров (ADR-0010).

## Выгрузка CSV

Выгрузка содержит то же, что видно в интерфейсе: метаданные и события без значений. Ячейка, которая начинается с `=`, `+`, `-`, `@`, табуляции или возврата каретки, получает спереди апостроф, чтобы табличный редактор не выполнил имя таблицы или пользователя СУБД как формулу. Журнал событий выгружается сервером, не больше 100 тыс. строк за раз, право на выгрузку — отдельная операция `exportAuditEvents`.

## Журнал действий операторов

ADR-0013. Создание, изменение и удаление источника, публикация политики, выпуск токена, регистрация и отзыв агента записываются в транзакции самого действия, с `sub` и именем пользователя из токена OIDC. У роли сервера в PostgreSQL на журнал есть только `INSERT` и `SELECT`: взломанный сервер может добавлять записи, но не может стереть или переписать уже сделанные. Значений настроек и паролей в журнале нет: изменение источника называет поля, а не их значения. Читают журнал администратор и аудитор организации.

## Черновик источника

Проверка подключения до сохранения не добавляет агенту новых команд. Черновик приходит в том же подписанном списке источников, что и сохранённый источник, с признаком `probe_only`. Агент применяет к нему те же проверки: хост и каталог журналов из локального списка разрешённых, пароль, запечатанный на адрес. Признак только сужает, что агент делает с источником: черновик открывается и проверяется, но не сканируется и его журналы не читаются. Взломанный центр, снявший признак, получает не больше, чем уже может, сохранив источник.

## Подделка контекста приложения (этап 3)

`VERIFIED` означает, что контекст подписан ключом приложения и не просрочен. Это подтверждает заявление приложения, а не присутствие человека. Скомпрометированное приложение с настоящим ключом может подписать чужой идентификатор.

## Что не считается обращением

Сборщик пропускает только запросы, которые не касаются ничего: `SELECT 1`, `SET`, `SHOW`. Вызов функции и чтение системного каталога всегда записываются: функция может читать таблицы, которых нет в тексте, а системные таблицы вроде `mysql.user` хранят хеши паролей.

## Известные остаточные риски

- **Память.** Go не гарантирует затирание: сборщик мусора копирует объекты, строки неизменяемы. Значения обрабатываются в `[]byte` с очисткой, но дамп памяти агента во время скана может их содержать.
- **Журналы СУБД на стороне заказчика** уже содержат литералы. Агент читает их, но не копирует. Защита самих журналов — задача заказчика.
- **Побочный канал custom-детекторов** описан выше.
